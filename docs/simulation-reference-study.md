## OpenStory：让人物有持续安排，让玩家能改变行动

### 源码中看到了什么

1. **计划有时间跨度。** `BasicPlanPlugin.py` 从地图可用地点生成长任务和分时安排；示例一次安排 12 个 Tick，并能重排剩余时间。计划不是每次只回答一句无上下文的话。
2. **新经历会改变计划。** `BasicReflectPlugin.py` 的具体实现检查近期记忆是否需要重排，并在较长周期回顾任务和经历。这里的反思与重排有实际调用逻辑。
3. **玩家介入是一种待执行事项。** 故事版 `BasicInvokePlugin.py` 读取 `user_plan:{agentId}`，核对 Tick，以较高优先级处理、消费一次，并把当前计划和动作提供给前端。其占用和优先级机制处理人物行动冲突。
4. **前端识别分支和快照。** `story/frontend/app.js` 维护当前分支、分支树及重连快照，向服务器请求分支树；快照同步与新 Tick 的呈现分开处理。
5. **接口存在不等于能力完成。** 本轮读取的 `BasicPerceivePlugin.py` 有 `pass` 占位方法，自省接口中也有占位部分。不能把接口名称或项目宣传直接当作每个模块已完整实现的证据。

### 在本项目中的具体落点

| 参考机制 | 大观园中的实现 | 取舍 |
| --- | --- | --- |
| 持续任务、剩余计划 | `planning.ts` 的 `AgentPlan` 保存目标、触发原因、最多四个语义步骤和记忆依据；院内移动后能继续读书、写字 | 四人、每 Tick 一次行动，保持可观察和可回滚 |
| 事件打断与自省 | 低精力、托付、新消息和不安会改变优先级；依据已有经历形成可查看的短自省 | 本地自省是有依据的文本整理，不宣称深度语言模型反思 |
| 玩家计划 | `queueDirective` 保存托付；只有完成动作或送达消息的 Tick 才消费。移动途中取消会回到原快照并保留待办 | 沿用单 Tick 事务，不引入 Redis/Ray 服务 |
| 分支、回看与重做 | 主世界、当前 IF、最多三条历史 IF；创建新 IF 自动保存旧线，恢复采用交换；同 Tick 对照 | 容量满时明确提示导出和删除，不静默覆盖历史 |
| 地图与人物行动一致 | 语义动作经 `rules.ts` 转成现有道路和院内路线，三维执行完成才记为到达 | 不让模型直接生成坐标、建筑或传送命令 |

## MiroFish：让经历可以追溯，让报告回答实际发生的事

### 源码中看到了什么

1. `simulation_runner.py` 把人物动作、轮次、时间与轮次汇总写入运行记录，并保存可检查的运行状态。
2. `zep_graph_memory_updater.py` 将动作组织成记忆片段，附来源、simulation_id、平台、首末轮次、人物 ID 和创建时间，并对批量文本规模设限。
3. `oasis_profile_generator.py` 使用资料为人物生成背景及关系。对大观园而言，这启发了“资料—人物—关系—行为”的链条，但本项目公开的文学资料继续来自已审阅的 `data/canon`。
4. `report_agent.py` 提供洞察检索、全景检索、快速搜索和人物访谈等工具；报告生成有每节工具调用和反思轮次上限。提示要求依据实际模拟记录，不编造工具输出、数字和发言。

### 在本项目中的具体落点

| 参考机制 | 大观园中的实现 | 可以核对的结果 |
| --- | --- | --- |
| 活动账本 | 完成事件含世界标识、Tick、人物、地点、目标、消息 ID、原因和记忆依据 | 纪事中可以展开“为何这样行动” |
| 记忆来源 | 知情记忆保存来源人物、原事件 ID、重要性；个人传播账本记录自己告诉过谁 | 新接收者须对应实际完成的对话事件；不会预装他人的秘密 |
| 多轮传播 | 人物找信任对象商议；接收者能先回应，再自行传播；自己的账本避免对同一人重复转述 | “消息流转”图只从完整快照里的转述事件画线 |
| 人物访谈 | 三种追问：打算、知情、信任；回答读取所选人物自己的状态与记忆，并列依据 | 未听到的消息不会出现在此人的回答中；标明“本地回应” |
| 报告与溯源 | `insights.ts` 导出 Markdown 纪要，列实际转述、当前状态、同刻差异和事件 ID | 不把未来快照、取消的 Tick 或生成的摘要作为已发生事实 |

## 与现有场景的深度融合

- **复用原园。** 四处精细庭院及其移动端模型、十五景、既有道路、水体、建筑和昼夜灯光全部继续使用。没有重建另一套地图。
- **走进院落。** 潇湘馆竹径、怡红院红香院庭、蘅芜苑蘅芷步道、秋爽斋诗席前庭设置舞台站位。人物经原门洞与铺地进入，离开时沿通路退回园路。配置在 `config/simulation.stage.json`。
- **让行动可见。** 同一套抽象人物小像表达行走、交谈、持书、书写和歇息；“临场 / 跟随 / 全园”控制观看位置，手动拖动解除自动跟随。
- **直接介入场景。** 点人像或“托付与追问”进入该人的手记；托付、追问、记忆、原文依据集中于同一人物。沉浸模式保留下一刻、暂停、速度和手记入口。
- **时间一致。** Tick 推进使用现有昼夜灯光，退出推演恢复游园原来的时间设置。1×/2×/4×只影响播放速度，不改世界步长和结果。

院内路线是**舞台导航**，并非原著精确平面或室内通行复原。`simulation:space` 对四院的高精度和移动端 GLB、四个人物站位进行身体高度和侧向余量的结构射线检查。通过结果见 `reports/acceptance/simulation-space.json`；它不等于完整导航网格验证，也不意味着植物绝不遮挡镜头。

## 文学证据、模拟设定与当前边界

原文摘录及出处继续从已审阅的 `data/canon` 发布；人物性格数值、情绪反应、对白、托付消息和推演结果属于虚构设置。消息不会写回文学资料。庭院站位和镜头属于场景演绎。

目前默认是可重复的本地规则推演，提供四名人物的持续计划、消息传播和互动。已适配可选的 DeepSeek-V4.1-Flash 服务端决策；默认本地模式可离线重复运行，真实模型的验收状态见 `docs/PROGRESS.md`。缺少服务器配置时界面明确显示未配置。远程模型仍只能选择经校验的语义动作与当前可知话语，不能任意编写状态修改。

本轮没有把 MiroFish 的大规模社会预测、外部图数据库，或 OpenStory 的完整分布式运行平台搬进项目，也没有声称复现它们的全部能力。报告是虚构世界的观察记录，不是现实预测。访谈为本地记忆整理；要得到开放式人物对话，仍需另行实现对话边界并评估人物一致性、事实约束和费用；当前模型接入负责条件解析、行动决策和小结。

## 验证入口

`npm test` 覆盖原有推演边界，以及持续计划、消息打断、多跳传播的来源、托付的执行和取消、分支保存交换、旧存档迁移、同刻比较与访谈依据。`npm run test:simulation` 在真实浏览器操作庭院到达、读书、访谈、消息图、分支恢复与手机沉浸流程。`npm run simulation:space` 检查院内结构净空。具体执行结果与部署记录统一记在 `docs/PROGRESS.md`，不能把上述入口的存在当作已经通过。
